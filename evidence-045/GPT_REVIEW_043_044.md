# 043 원본 + 044 수정본 통합 검수

검수일: 2026-10-29 · 대상: 수학의지혜 StudyCheck 연계 프로젝트

## 결론

- **044의 ‘전역 정렬 후 3개 → 지정 ID 3개’ 선정 수정은 제한된 검수 범위에서 수용한다.** 기본 후보 3개, 대체 1개(세 번째 자리 교체), 소스 대기 1개의 구분을 유지한다. 같은 목록 조회나 추가 영상 제작을 요구하지 않는다.
- **043 운영 설치 SQL은 실행 보류다.** 이유는 원본 미확보가 아니라, 이번에 확인한 실행 권한·호출자 검증·중복 문맥·반환/복원 문제다.
- **운영 연결이 승인·키만 기다리는 상태는 아니다.** 실제 API는 계속 운영 모드를 거부하며 엔진은 시연 카탈로그/파일 저장소를 직접 사용한다. 이것은 코드 작성이 남았다는 뜻이다.
- 이미 만든 로컬 시연판, 기반 DB, 표본 이미지, 영상 지도는 폐기/재검증하지 않는다. 다음 작업은 한 학습 흐름을 실제 provider 인터페이스에 연결하고 저장 신뢰 경계를 닫는 구현이다.
- 학생 공개·유료 호출·운영 DDL/DML·운영 SDK 접속을 이번 검수만으로 승인하지 않는다.

043 시험 위에 044를 덮었을 때의 실패에는 대표예제 우선·시연 관계 변경과 옛 시험의 기대값 충돌이 포함된다. 044 묶음은 기존 시험의 최신본을 제공하지 않는 부분 묶음이라고 스스로 밝힌다. 따라서 ‘869 성공이 거짓’ 또는 ‘044 전체 앱이 실패’라고 확대하지 않는다. 다만 **실제 통합 브랜치와 그 판의 시험을 함께 검수할 수 있게 제출해야 한다.**

## 3. 수용되는 044 수정

- `firstSet.ts`는 확인된 ID 3개를 우선순위대로 선택한다. 조회 반환 순서나 전역 LIMIT 때문에 한 유형이 탈락하는 경로를 제거했다.
- 선택한 ID가 없으면 다른 영상을 자동으로 채우지 않는다.
- 소스 식별값 존재, 재생 확인, 학생 접근, 노출 검수, 확인문제 준비를 분리하고 미확인을 성공으로 만들지 않았다.
- 영상 06은 식별값 대기 상태로 남기며 제작 파일 부재로 해석하지 않는다. 영상 07은 세 번째 자리 대체 후보이지 네 번째 추가가 아니다.
- 유형 중복 태그는 읽은 목록에서만 중복 제거한다. 운영 정리 SQL을 요구하지 않는다.

단, 장면값 검사에 `Number(scene.start)`/`Number(scene.end)`를 사용하여 **null이 0초로 변한다.** 직접 adapter 탐침에서 `start:null,end:null`이 `0–0` 구간으로 생성됐다. 이는 영상 선정 방향의 실패가 아니라 연결 전 반드시 고칠 작은 값 검증 오류다. `typeof === 'number'`, finite, `0 <= start < end <= duration` 등 실제 계약을 검사하고 미확인은 그대로 남긴다. 순번이나 메타 길이로 초를 만들지 않는다.

## 4. R045-01 — 운영 저장 함수의 신뢰 경계 (설치 전 필수)

**근거:** `docs/sql/migrations/043_learning_actions.sql` 136–213행, 특히 147·151–164·181–182·211–213행. 043/044 동일.

1. 함수는 SECURITY DEFINER이며 `p_student_id`, `p_graded`, `p_watch_log_id`, `p_producer`, 실행 범위를 외부 인자로 받는다. 함수 안에는 호출자의 권한/학생 범위/과제 배정/대상 문항·시청 기록 소유권 확인이 없다.
2. `p_graded`는 DB가 채점한 값이 아니다. **인자로 받은 값을 그대로 INSERT**한다. ‘DB 함수가 채점을 정한다’는 주석과 다르다.
3. 실행 권한은 PUBLIC만 revoke한다. `anon`·`authenticated` 직접 권한 회수와 신뢰 서버 역할의 명시적 grant가 없다. 직접 역할 기본권한이 남는 환경에서는 PUBLIC revoke만으로 막히지 않는다. 반대로 기본권한이 없는 환경에서는 의도한 서버 역할도 호출하지 못할 수 있다.
4. `search_path = public`을 안전한 경로 설정으로 바꾸고 필요한 이름을 스키마 한정한다. 기존 프로젝트 전체 기본권한을 바꾸는 방식이 아니라 이번 객체만 제한한다.

**판정 범위:** 실제 운영 ACL을 조회하거나 악용하지 않았다. 현재 운영에 취약 함수가 설치됐다고 주장하지 않는다. 본 SQL은 환경별 기본권한에 의존하고, 실행이 허용된 호출자에게 위 범위를 검증하지 않는다는 코드 검토 결과다.

**정해 둘 구현 방향:** 이 최초판의 채점값 포함 쓰기 RPC는 서버 전용으로 제한한다. PUBLIC/anon/authenticated의 직접 실행을 명시적으로 차단하고, 필요한 서버 역할만 허용한다. 서버 API에서 현재 학생 인증·활성 상태·배정·원문·실행 범위를 검증한 뒤 서버 채점 결과만 전달한다. SQL도 payload 모양, 문맥의 일치, 참조 소유권, 역할 경계를 방어적으로 확인한다. SECURITY DEFINER 안의 `current_user`는 호출자가 아니라 함수 소유자가 될 수 있으므로 그것만으로 호출자 역할을 판별하지 않는다.

공식 근거(외부 검증, 제출물과 구분):
- Supabase Database Functions: https://supabase.com/docs/guides/database/functions
- Supabase revoke 안내: https://supabase.com/kb/troubleshooting/how-can-i-revoke-execution-of-a-postgresql-function-2GYb0A
- PostgreSQL 17 CREATE FUNCTION: https://www.postgresql.org/docs/17/sql-createfunction.html

## 5. R045-02 — SQL 중복 판정과 저장 문맥 (설치 전 필수)

**근거:** SQL 160–207행, `supabaseStore.ts` 61–96·105–155행.

- 시도를 **먼저 INSERT/UPDATE한 뒤** 중복/충돌을 판정한다. 중복에도 `updated_at`가 변하고, 다른 문항/run으로 들어온 같은 행동 ID에는 새 시도 생성이 먼저 일어난다.
- 중복 동등성은 `occurred_at + payload`만 비교한다. RPC 인자의 `kind`, 문항, source_kind/ref, run, watch context는 별도로 검증하지 않는다. payload가 그 값을 반드시 포함하고 인자와 일치한다는 보장도 없다. 같은 payload와 시간을 둔 채 별도 인자를 바꾸는 요청이 ‘중복’으로 분류될 여지가 코드상 존재한다.
- 시도 유일키 `(student_id, problem_id, run_id)`는 다른 과제에서 같은 문항을 푸는 시도를 합칠 수 있다. 기존 시도 키(과제·문항·학생)를 운영 구현에 보존하거나 동등하게 표현해야 한다.
- 유일키만으로 동시 요청의 중복/충돌 의미가 해결되지는 않는다. **같은 행동 키 기준** 직렬화/원자적 재판정이 필요하다. 같은 시도 upsert의 잠금이 같은 행동을 다른 시도로 보내는 경우까지 보장한다고 가정하지 않는다.
- 신규 성공 반환에는 `graded`가 빠져 있어 adapter에서 null이 된다. 중복 반환에는 있다. 첫 성공/재전송 결과의 계약을 맞춘다.
- 충돌 경로의 `v_changed := v_changed || 'payload'` / `'occurred_at'`는 미지정 문자열을 배열로 해석하는 연산자 중의성이 있다. `array_append` 또는 명시적 text[]을 사용한다. 이는 **PG 엔진 재현 결과가 아니라** 공식 배열 연산 설명과 원본 SQL의 대조다.

필요한 시험: 정상, 동일 재전송, 같은 ID/다른 kind·과제·문항·run, 서로 다른 학생, 같은 키 동시 요청, payload 정규화, 변경필드 충돌, 저장 중 실패. 중복·충돌의 감사 수신 기록을 허용하더라도 학습 상태/시도 생성/계획 갱신을 조용히 진행하지 않는다.

공식 배열 연산 근거:
- https://www.postgresql.org/docs/17/arrays.html
- https://www.postgresql.org/docs/17/functions-array.html

## 6. R045-03 — 운영 경로 연결은 아직 코드 작업이 남음

**직접 실행:** `app/api/learning/act/route.ts` POST를 운영 모드·합성 설정으로 호출하면 **403, SDK 생성 0**. 실제로 50–52행에서 반환한다. 직원 허용을 대역으로 주입해도 `teacher/route.ts`는 **501**을 반환한다. 이는 실제 직원 인증 성공을 검증한 것이 아니라 그 뒤 연결 부재를 확인한 것이다.

- `session/route.ts`는 시험 입장 코드만 처리한다.
- `engine.ts`는 `catalog.ts` 값과 `testStore()`를 직접 사용한다. 작성한 content/auth/store provider가 실제 학습 경로에 주입되지 않는다.
- 운영 문제는 `stem:''`, `choices:null`, `imagePath`를 반환하지만 학생 화면은 지문과 보기만 렌더링하며 실제 문제 이미지를 표시하는 연결이 없다.
- 운영 영상은 YouTube embed URL을 반환하는데 현재 화면은 HTML `<video src>` 경로다. 기존 YouTube 플레이어를 사용하도록 매체 형식 연결이 필요하다. 운영 재생 성공을 검증한 것은 아니다.

**결정:** 이 작업은 이미 승인된 구현 범위다. ‘운영 접속 전이라 작성하지 않는다’로 남기지 않는다. 실제 route→인증/배정→콘텐츠→서버 채점→RPC→재조회→강사 요약을 주입 가능한 실제 경로로 완성하고 합성 provider로 끝에서 끝까지 먼저 시험한다. 데모 기본 차단을 삭제하는 것이 아니라 모드별 의존성을 명시적으로 연결한다. 운영에서는 데모를 대체 저장소로 쓰지 않는다.

## 7. R045-04 — 저장/응답 계약의 누락

### 7.1 학생 응답에 해설 경로가 남음

`catalog.ts` 54–63행의 `forStudent()`는 `answer`만 뺀다. 독립 탐침에서 `answerImagePath:'private/answers/synthetic.png'`가 그대로 남았다. **실제 해설을 읽거나 노출한 사건이 아니다.** 운영 연결 전에 학생용 반환 필드를 명시적으로 허용 목록화하고 해설 경로·모범답·내부 검수 이유를 제외한다.

### 7.2 다시 읽으면 과제·도움 맥락이 달라짐

`supabaseStore.loadAttempt()`는 `source_kind/ref`를 읽지 않고, `emptyAttempt()`의 세 번째 `taskId` 자리에 `problem_id`를 넘긴다. 합성 조회에서 과제 `task-X`가 `101`로 복원됐다.

`engine.payloadOf(help)`는 `relation_ref`, `observed`를 쓰지만 `content_ref`, `segment_key`를 담지 않는다. 저장소 복원기는 그 없는 두 값을 읽어 `contentRefId:''`, `segmentKey:'full'`로 만든다. 직접 동일한 payload 형식으로 재현했다. 실제 데이터를 복원한 것은 아니다.

도움 시점의 **검증된 자산·버전·구간·원문·과제 연결**을 불변 근거로 보존한다. 학생 원요청/중복판정 의미와 서버에서 검증·산출한 관측을 분리한다. 날것의 client claim을 재조회 때 검증된 관측으로 읽지 않는다. 영상 관련 기존 표에 쓰지 않는 단계라면 재사용이 완료됐다고 기록하지 않는다.

### 7.3 인증 조회 오류를 ‘학생 없음’으로 취급

`supabaseAuth.ts` 62–77행은 session 조회 error를 검사하지 않고 user_id로 넘어간다. 합성 오류 뒤 fallback 행을 주면 `deny:null`이다. 활성 상태 검증도 없다. 오류와 정상 0행을 분리하고 기존 학생 로그인·권한 규칙을 재사용한다. user_id fallback을 쓸 것이라면 기존 권한 모델/RLS와 같은 의미여야 한다.

### 7.4 연결 시 함께 고칠 작은 입력 문제

- `Number(problemId)`가 큰 bigint 문자열을 다른 숫자로 바꾼다. 탐침 `9007199254740993 → 9007199254740992`. 현재 운영 ID가 그 크기라고 주장하지 않는다. ID는 문자열로 일관되게 넘긴다.
- 새 자유입력 객관식 채점은 `30`을 `③` 정답으로 처리한다. checkbox의 숫자배열 규칙을 자유문자열에 무검증으로 적용하지 않는다. 먼저 유효한 보기 토큰인지 검사한다.
- 장면 null→0초는 §3과 같이 수정한다. 첫 장면을 무조건 추천구간으로 선택하지 않고 검수한 구간을 쓴다.

## 8. 콘텐츠 관련 결정을 미루지 않는다

1. 첫 학습 세트는 기존 두 유형, 원문/확인문제 합계 최대 10개, 영상 최대 3개다. 새 영상·새 문제은행·전수검수는 선행조건이 아니다.
2. 대표예제 우선·필요 개념 글 안내라는 **브리핑에 기록된 윤T 방침**을 유지하되, 종류만으로 모든 축에 같은 경로를 강제하지 않는다. 기본 후보에 알맞은 대표풀이가 없으면 확인된 대체 후보의 적합성을 검토하거나 검수된 카드로 연결한다. 미검수 콘텐츠를 자동 생성해 공개하지 않는다.
3. 노출 검수: 현재 원문의 최종 답/정답 번호/그 원문의 완성 풀이가 영상 전체나 다른 제공 경로로 바로 드러나면 질문 도움용으로 승인하지 않는다. 일반 공식·다른 예제의 풀이를 ‘정답 포함’이라는 이유로 일괄 금지하지 않는다.
4. ‘개념 Check 정답’의 존재는 영상 전체 금지 사유가 아니다. 그 답을 보고 같은 문제를 맞힌 것을 독립 해결로 기록하지 않는다. 첫 확인은 **검수된 기존 다른 문항**을 우선한다. 증명 목적은 근거 확인 질문/빈칸 등을 써도 되지만, 자동판정 불가이면 완료·정답으로 위장하지 않는다.
5. 처음 소수 관계는 서버 전용 버전 있는 승인 명세 파일로 준비해도 된다. 새 검수 테이블/UI를 다 만든 뒤에야 첫 시범을 시작하도록 확대하지 않는다. 개발자가 후보·근거·노출 범위를 한 화면으로 준비하고 윤T/지정 검수자가 묶음 확인한다. 같은 승인 관계를 학생마다 재검수하지 않는다.
6. 학생 접근 권한은 콘텐츠 품질 승인과 별개이며 **현재 학생/과제에 대해 요청 때 확인**한다. ‘학생 접근 yes’를 모든 학생의 공통 승인값으로 사용하지 않는다.

## 9. 격리 PostgreSQL 검증

현재 GPT 환경에는 native PostgreSQL/psql이 없었다. 검수 컨테이너에서 도구 확보를 시도했지만 패키지 소스 접근 문제로 완료하지 못했다. **실제 PG 실행 통과를 주장하지 않는다.** SQLite/JS 모형을 PostgreSQL 실행 증거로 쓰지 않는다.

Claude에게 폐기 가능한 로컬 PostgreSQL 17 계열(기설치 엔진 또는 개발용 컨테이너)을 준비해 원본/수정본 DDL을 합성 fixture에서 검증하도록 지시한다. 운영 DB를 첫 쓰기 시험장으로 쓰지 않는다. 설치용 도구가 필요한 경우 앱 의존성과 분리하고 공식 배포원을 사용하며, 실제 운영 키/환경파일/데이터를 읽지 않는다. Docker 등 컨테이너는 외부 포트 공개 없이 로컬로만 접근한다.

검증에는 **직접 역할 기본 execute 권한이 있는 경우와 없는 경우**, anon/authenticated/service 역할별 호출, 학생 A/B/직원, 실패 롤백과 동시 요청을 포함한다. 함수 실행 권한과 RLS 접근을 각각 확인한다. 보고에는 엔진 버전·fixture·명령·종료코드·실제 결과를 남긴다.

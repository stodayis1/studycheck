# 보안 모델

2026-09-16 전면 점검·강화. 그때 무엇을 왜 했는지 남긴다.

## 대원칙 3가지

### 1. 학생·학부모도 Supabase에서는 `authenticated`다
익명 로그인을 쓰기 때문이다. 그래서 `to authenticated using (true)` 정책은 **학생에게도 열린다.**
직원 전용 데이터는 반드시 `using (public.is_staff())`.

### 2. 서버 API는 RLS를 통째로 우회한다
`app/api/*`는 service_role 키를 쓴다. 인증 검사를 빼먹으면 그 순간 인터넷 전체에 열린다.
새 API를 만들 때는 **무조건** 첫 줄에:
```ts
const deny = await denyIfNotStaff(req)   // lib/apiAuth.ts
if (deny) return deny
```
브라우저에서 부를 때는 `apiFetch`(`lib/apiFetch.ts`)를 쓴다. 토큰을 자동으로 붙인다.

### 3. 잠그기 전에 "누가 읽고 있는지" 전수조사한다
RLS를 조이면 화면에서 데이터가 조용히 사라진다. 사용자는 이걸 제일 싫어한다.
`grep -rn "from('테이블명')" app components lib` 로 **브라우저에서 직접 읽는 곳**을 먼저 찾을 것.
서버 API를 거치는 것만 있으면 안전하게 잠글 수 있다.

| camp_students, camp_progress | 공개 읽기·수정 (공개 현황판). 삭제 권한은 회수함 |

## 로그인

- **선생님**: Supabase Auth. `public.users.role`이 admin/teacher/staff
- **학생·학부모**: 익명 로그인 → `student_login(login_id, phone_last4, role)` RPC
  - 이름 + 보호자 전화 뒷 4자리
  - 성공하면 익명 uid를 기록 → 이후 RLS가 본인 것만 열어준다.
    **학생은 `students.session_uid`, 학부모는 `students.parent_session_uid`** (아래 참고)
  - **15분에 5회 실패 시 15분 잠금** (`student_login_attempts`). 성공하면 실패 기록이 지워진다
  - 같은 역할끼리는 마지막 기기 하나만 유지된다. 학부모가 폰과 PC에서 번갈아 로그인하면
    마지막 것만 살아있다 (원래 동작)

## 2026-09-22 1단계 — 인증 없이 열려 있던 서버 라우트 차단

두 앱을 전수조사(`app/api/*` / OPS `src/app/api/*` + 양쪽 RLS 정책)한 결과, service_role 키로 돌면서
인증 검사가 아예 없는 라우트가 StudyCheck 5개 · OPS 9개 있었다. URL만 알면 누구나 호출되는 상태였다.
1단계에서 **가드만** 붙였다 (DB 정책은 2단계).

**StudyCheck**

| 라우트 | 무엇이 가능했나 |
|---|---|
| `api/push/send` | 인증 없음 + `target` 생략 시 전체 브로드캐스트가 기본값 → 전 학부모·학생에게 임의 푸시 |
| `api/generate-feedback`, `api/parse-records` | 학원 `ANTHROPIC_API_KEY`가 외부인의 AI 프록시로 쓰임 |
| `api/send-kakao` | 인증 없이 알림톡·문자 발송 |
| `api/sync-absence-to-ops` | `OPS_SYNC_SECRET`을 대신 붙여줌 → 비밀키 없이 OPS에 결석 주입 |
| `api/push/subscribe` | **남의 `studentId`로 구독 등록 → 그 학생의 알림을 자기 기기로 수신** |

`push/send`는 `target`을 반드시 명시해야 하도록 바꿨다(전체 발송은 `{ broadcast: true }`).
`push/subscribe`는 직원 전용이 아니라 학생·학부모도 부르는 곳이라 `denyIfNotStaff`를 쓸 수 없어서,
토큰으로 본인 확인 후 `students.session_uid = auth.uid()`가 맞을 때만 저장하고
body의 `studentId`/`userId`는 믿지 않고 토큰 주인으로 덮어쓴다.

호출부 11곳은 `fetch` → `apiFetch`로 바꿨다 (토큰 자동 첨부). **새 라우트를 만들 때 이걸 빼먹으면
화면에서 401이 난다.**

**수학OPS**

OPS에는 가드 헬퍼 자체가 없어서 `src/lib/apiAuth.ts`를 새로 만들었다. StudyCheck와 달리 **쿠키 세션
기준**이다(OPS는 브라우저에서 같은 출처로 fetch하므로 쿠키가 자동으로 실려온다).

```ts
const deny = await denyIfNotStaff()   // 원장 전용이면 { adminOnly: true }
if (deny) return deny
```

- `getSession()`이 아니라 **`getUser()`**를 쓴다. `getSession()`은 쿠키의 토큰을 검증 없이 믿기 때문에
  서버에서 신원 확인용으로 쓰면 안 된다. (기존 `api/db/route.ts`는 아직 `getSession()` 방식 — 3단계에서 정리)
- 쿠키가 없는 서버→서버(크론)에서는 반드시 막힌다. 그런 작업은 이 라우트를 fetch하지 말고
  `src/lib/sendSms.ts`처럼 로직을 직접 호출할 것.
- 적용: `studycheck/create-student` · `deactivate-student` · `set-leave`, `makeups/upload`,
  `onboarding/send`, `consultations/send-kakao`, `absences/push-to-studycheck`, `sms/send`, `special/sms`
- `sms/send`·`special/sms`는 그때까지 `academy_settings` RLS 때문에 **우연히** 막혀 있었을 뿐이다
  (비로그인 상태에서 솔라피 키를 못 읽어서 실패). 정책 한 줄 바뀌면 열리는 상태였다.

**일부러 열어둔 것 (건드리지 않았다)**

- StudyCheck `api/grade/[code]`, `api/grade/[code]/photo` — 학생이 QR로 스스로 채점하는 경로
- StudyCheck `api/push/unsubscribe` — endpoint 자체가 추측 불가능한 값이라 그걸 아는 사람만 해제 가능
- OPS `api/makeup`, `api/core-test-booking`, `api/saturday-notice`, `api/consultation-record`,
  `api/special/register` — 학부모가 로그인 없이 쓰는 토큰 링크 페이지

**부작용으로 알아둘 것**

- 인증 확인이 요청마다 한 번 붙어 라우트가 건당 0.1초쯤 느려진다. 문자 50건 일괄이면 총 5초 추가.
- 학생이 **같은 역할로** 새 기기에서 로그인하면 세션이 새 기기로 넘어가므로, 이전 기기에서는 알림 켜기가
  403이 된다(그 기기는 이미 대시보드도 안 보이는 상태다). 다시 로그인하면 정상.
- `/admin/test-kakao`는 로그인 상태에서만 작동한다.

## 2026-09-22 학부모 세션 분리 (보안이 아니라 '화면이 비는' 문제)

`student_login`이 학생·학부모 구분 없이 `students.session_uid` **한 칸**에 덮어써서, 나중에
로그인한 쪽이 먼저 로그인한 쪽을 밀어내고 있었다. 밀려난 쪽은 RLS가 막아 대시보드가 비고
로그인 화면으로 튕긴다.

실측 (2026-09-22, 재원생 192명):

| | 인원 |
|---|---|
| 학생·학부모 양쪽 다 로그인한 적 있음 | 54명 |
| 그중 최근 30일 내 | **52명** |

**고치는 순서 — 지키지 않으면 학부모 화면이 빈다.** 전부 추가·확대만 하고 데이터는 지우지 않는다.

1. `docs/sql/학부모세션분리_1_칸추가와정책확대.sql`
   — `parent_session_uid` 칸 추가 + `session_uid`를 쓰는 정책 12개를 `session_uid` 또는
   `parent_session_uid`로 넓힌다. **이 시점에는 동작이 하나도 바뀌지 않는다** (새 칸이 전부 NULL이라
   OR 조건이 항상 false). 그래서 중간에 아무도 잠기지 않는다.
2. 앱 배포 — `app/api/push/subscribe`가 두 칸을 모두 본다
3. `docs/sql/학부모세션분리_2_로그인함수.sql`
   — 이때부터 학부모 로그인이 새 칸에 기록된다

정책이 두 칸을 모두 받아주므로 2번 함수를 되돌려도 아무도 잠기지 않는다.

`session_uid`를 쓰는 정책이 12개나 되므로(class_sessions, feedbacks, learning_notes,
progress_checks, schedules, student_exam_prep, student_textbooks, student_worksheets,
video_watch_logs, exam_prep_assignments, feedback_replies, students) **하나라도 빠뜨리면 그 화면만
조용히 빈다.** SQL 파일 끝의 확인 쿼리로 12줄이 다 나오는지 볼 것.

**2단계(DB 정책) 대기 — 코드가 아니라 RLS라서 앱을 고쳐도 안 막힌다**

4. **OPS 15개 테이블에 `INSERT ... using(true)` + anon INSERT 권한.** `students`, `attendances`,
   `consultations`, `sms_logs`, `payment_notices`, `makeups`, `textbooks`, `inventory` 등.
   브라우저에 공개된 anon 키만으로 로그인 없이 행을 넣을 수 있다(명단 오염).

   `ensure_saturday_slots`는 **비로그인 상태로 실행 가능**.

8. **`admin_add_academy_event`의 비밀번호가 DB 함수 안에 평문**(`'수학의지혜2026'`)이고 anon 호출 가능.

## 키 교체 절차 (2026-09-16에 실제로 한 순서)

Supabase가 옛날 `anon`/`service_role` 키를 2026년 말에 없앤다. 이미 새 키로 넘어갔다.

- `NEXT_PUBLIC_SUPABASE_ANON_KEY` = `sb_publishable_...` (브라우저 노출 OK)
- `SUPABASE_SERVICE_ROLE_KEY` = `sb_secret_...` (**절대 노출 금지**)

**순서를 지키지 않으면 앱이 멈춘다:**
1. Supabase → Settings → API Keys 에서 publishable / secret 키 확보
2. Vercel 환경변수 **두 개 모두** 교체 (이름은 그대로, 값만)
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 Type을 **Config**로 해야 저장된다 (Secret이면 거부됨).
     타입 변경이 안 되므로 **지우고 새로 만들어야 한다.** Environments는 Production and Preview.
3. Redeploy
4. **동작 확인** — 학생 로그인 / 선생님 학생관리 / 문제은행 / 채점결과
5. 전부 통과한 뒤에야 Supabase → API Keys → Legacy 탭 → `Disable JWT-based API keys`
   (anon과 service_role을 **한 번에** 끈다. 따로 못 끈다. 되돌리기는 가능)
6. 로컬 `.env.local`도 새 키로 바꿔야 업로드 스크립트가 돈다

옛날 키는 2026-09-16에 비활성화 완료.
